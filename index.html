edge & quantization

How much of a detector survives 10.6 MB → 4.4 MB?

The cigarette detector from the companion study, exported once to ONNX and then quantized four ways: FP32, FP16, dynamic INT8, and static QDQ INT8 calibrated on training frames. Every variant is scored on the same 1,370 held-out images with pycocotools and timed on a laptop CPU, so accuracy and milliseconds are measured on the same runs.

Short answer: 58% smaller and 1.37× faster for 0.93 mAP, with small-object AP moving -1.96. The 320 px input is the bigger speed lever and the much worse trade.

Input size is the bigger lever

Before quantizing anything, the cheapest speedup is asking the network to look at fewer pixels. That works, and then it stops working — small objects are the first thing to go, because a cigarette only spans a handful of pixels once the frame is squeezed to 320 px.

FP32 · 320 → 640 px
Input mAP AP small ms FPS
320 pxfp32 41.8 14.4 7.0 141.9
416 pxfp32 48.0 23.2 14.6 68.7
512 pxfp32 50.9 28.3 18.4 54.3
640 pxfp32 52.1 31.3 31.8 31.4

Going 640 → 320 px is 4.51× faster and costs 10.2 mAP, of which 16.9 comes out of small-object AP. Input size is the bigger speed lever — 4.51× against 1.37× for quantization — but it is also the lever that throws away the objects the detector exists to find.

The honest reading: shrinking the input is not free compression — it changes what the model can see. Quantization changes how the numbers are stored; input size changes the information available. For a cigarette detector, quantization is the better deal.

Static quantization detail

Calibration uses 256 random training frames, MinMax range, per-channel weights. Validating on the images that shaped the activation ranges would quietly flatter the quantized model, so the calibration set never overlaps the evaluation split.

The exported graph is a QDQ model (QuantizeLinear/DequantizeLinear around every conv), which is the format ONNX Runtime prefers for integer kernels and the format ONNX Runtime Web can execute in WebAssembly.

What the measurements say

Including the part where the earlier paper's YOLO row does not reproduce.

read this before quoting a number
01

One layer decided whether the quantized model worked at all

The Detect head ends in a Concat that puts box coordinates (0–682 px) and class probabilities (0–1) in the same tensor. Calibrating a single scale over it gives a 2.7-pixel step, so every probability below 0.5 dequantized to exactly 0. The graph still loaded, still ran at 20 ms, and returned zero detections — AP 0.00. Keeping the output Concat in float brought it back to 39.0 mAP.

02

The head, not the backbone, is what quantization breaks

After the output fix the model still lost 13 mAP. The loss sits in the Detect head, where the DFL branch regresses sub-pixel box offsets and the score branch needs fine resolution. Quantizing the backbone and neck while leaving the head in float lands at 51.14 mAP against 52.07 — a cost of 0.93 mAP and 1.96 AP small — for 4.4 MB instead of 10.6 MB. Mixed precision is the only version of INT8 that survived contact with this detector.

03

On a CPU, INT8 buys size, not a big multiplier

The shipped graph runs 1.37× faster than FP32 (23.2 ms vs 31.8 ms) and is 58% smaller. That is a real win, but it is not the 3–4× that quantization posts usually promise: this detector is small enough that kernel-launch and memory traffic dominate, and the head — a meaningful share of the compute — is still float. Checked against the optimized graph, 63 convs do run as QLinearConv; the speedup is limited by the model, not by a failed fusion.

04

Dynamic INT8 is an order of magnitude slower on a CNN

Dynamic quantization needs no calibration data, which makes it the tempting one-liner. Here it costs 5.85 mAP and runs at 317 ms/image — 10.0× slower than FP32 and 13.7× slower than the static graph. It emits 88 ConvInteger nodes with a fresh activation quantizer in front of each; that path is tuned for MatMul-heavy transformers, not for a convolutional detector.

05

FP16 halves the file and changes nothing on CPU

FP16 lands at 5.3 MB with statistically identical accuracy (52.03 vs 52.07 mAP) and runs at 32.1 ms — slower than FP32's 31.8 ms, because the CPU runtime casts back to FP32 for most kernels. It is a download-size optimization for GPUs, not a CPU one.

06

Input size is the bigger lever, and the more expensive one

640 → 320 px is 4.5× faster — more than quantization delivers — but it costs 10.2 mAP, of which 16.9 points are small-object AP (31.3 → 14.4). A cigarette is a handful of pixels at 320 px. Quantization is the cheaper trade for this task; halving the input is the cheaper trade only if the objects are large.

07

Threads change the number you should quote

Static INT8 drops from 58.9 ms on one thread to 27.3 ms on 16 threads — and it is actually fastest at 8 threads (24.0 ms), because hyperthread contention costs more than the extra cores return. The FP32 gap between 1 and 8 threads is 2.8×, and the INT8 advantage shrinks as threads are added (1.32× at one thread, 1.15× at eight) because integer convs do not scale as well. A GitHub Pages visitor only ever gets one thread, so the demo's counter reads the slow end.

08

The earlier paper's YOLO row does not reproduce

The companion study lists YOLO11 at mAP 40.4 and mAP75 35.2. Re-running the released checkpoint under the standard COCO protocol gives 52.1 and 53.5, while mAP50 agrees (88.0 measured vs 88.5 reported). Same checkpoint, same split, so the original table most likely used a different scoring protocol or a confidence floor. This study does not repeat 40.4: it measures every variant locally and uses the measured FP32 run as the baseline.
